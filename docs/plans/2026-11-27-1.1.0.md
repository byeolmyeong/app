## 내 결정(묻지 않고 고른 기본값 — 각 저장소의 새 결정에서 확정)
- 이 계획 파일은 앱 저장소에 둔다(1.0.0 계획과 같이). 서버 · 어드민 · 랜딩의 결정은 그 묶음을 할 때 그 저장소에 쓴다.

- 1.0.0 수령자 판정의 기준 시각은 서버 설정 하나(`byeolmyeong.purchase.legacy-cutoff`, 제안 — 1.1.0 서버 운영 배포 시각). 그 전에 만든 나 탭 풀이 · 시기 풀이 행이 하나라도 있으면 상품이 있는 것으로 본다.
- 궁합 하루 안전 한도는 **50**(104 의 세션 예시), 몰림 묶기는 **10분 안 3명 넘게**(104 의 예시) — 서버 설정값으로 두고 운영 로그를 보고 바꾼다.
- 궁합 하루 한도는 DB 로 센다(그날 한국 날짜에 만든 내 궁합 수). 지금 생성 한도(`GenerationQuota`)는 서버 메모리라 재시작 · 블루그린(서버 046) 때 초기화된다.
- "나왔어요" 알림의 "앱을 닫았을 때": 서버는 완성 뒤 **30초 안에 그 궁합의 결과를 받아 가지 않으면** 알림함 + 푸시를 보낸다(제안 — 앱이 화면을 떠났는지 서버가 알 길이 없어서). 받아 갔으면 보내지 않는다.
- 밤 무음(21:00 ~ 08:00 한국 시각)은 궁합 · 공지 알림 모두에 같은 규칙: iOS 는 `sound` 를 빼고, 안드로이드는 조용한 채널(`quiet`, 앱이 만든다)로 보낸다.
- 링크 코드는 짧은 무작위 8자(대문자 + 숫자, 헷갈리는 글자 뺌). 주소 경로는 **`/i/{code}`**(결정 111) — 랜딩 `byeolmyeong.com/i/…` · 웹 앱 `app.byeolmyeong.com/i/…` · 앱 라우트 `/i/[code]` 모두 같다.

### 서버 (byeolmyeong-api)

#### S① 결제 확인 (서버 `feat/entitlement`) · 결정 101 · 서버 결정 052(제안 "자세한 풀이 상품 확인")

- S1-2 entitlement-check: `report.EntitlementPolicy.allows(ownerId, kind)` 안에 — ① 1.0.0 수령자(기준 시각 전 나 탭 풀이 · 시기 풀이 행이 하나라도) → true ② RevenueCat 구독자 조회의 상품(entitlement 이름 제안 `detail`)이 있으면 true ③ 아니면 false → 402 `PURCHASE_REQUIRED`(지금 자리 그대로, 생성 한도를 세기 전). 조회 결과는 계정마다 짧게(1분, 제안) 메모리 캐시. RevenueCat 이 실패하면 **허용하지 않고** 503 `PURCHASE_CHECK_FAILED`(제안 — 돈 받지 않고 열어 주지 않게).
- S1-3 entitlement-read: 앱이 결제 시트 · 마이에 "샀음"을 보일 수 있게 `GET /entitlements` → `{ detail: boolean }`(제안, 세션). 앱은 이 값으로 화면만 바꾸고, 받기 가능 판정은 여전히 402.

#### S② 궁합 v2 핵심 (서버 `feat/synastry-v2`) · 결정 104 의 2 ~ 6 · 11 · 서버 결정 053(제안 "궁합 v2 — 사이 둘 · 상대 출생 정보 저장 · 한 번에")

- S2-2 relation-two: 입력은 `LOVE` · `FRIEND` 만(`WORK` · `FAMILY` 는 400 `INVALID_RELATION`). enum · 가중치 · DB 제약은 옛 기록을 읽으려고 남긴다. 친구 글 프롬프트를 "가까운 사이"(가족 · 동료와 읽어도 어색하지 않게) 말투로. `scoreLabel` 은 응답에서 빼거나 남겨도 앱이 쓰지 않는다(아래 "서버 코드에서 본 것" 5).
- S2-3 partner-birth: V36 `synastries` 에 상대 출생 정보 칸(생년월일 · 시각 null · 곳 id null)과 `source`(DIRECT · LINK). 그 궁합에만 쓴다. 궁합 · 계정을 지우면 함께 지워진다(이미 cascade). 로그 · 감사 detail 에 넣지 않는 테스트.
- S2-4 one-shot: 만들기를 비동기 하나로 — `POST /synastry`(제안, 202 `{ id, status: WRITING }`) → 요약(키워드 · 한 줄) 다음 네 영역 동시 → `DONE`. `GET /synastry/{id}` 가 `{ status, score, headline, keywords, reasons[], report? }`(제안 — `reasons` 는 이유 펼침의 별 이름 · 각도, 상대 출생 정보가 저장돼 있어 읽을 때 계산). 실패는 `FAILED`(061 틀, 다시 보기 = 같은 경로 다시). 옛 `POST /synastry/direct` · `POST /synastry/{id}/report` 는 1.0.0 앱이 부르지 않으므로 이 묶음에서 바꾸거나 지운다(서버 결정 053 에 적음).
- S2-5 recalc-on-profile-change: `profile.BirthProfileChanged` 를 들으면 직접 넣은 궁합의 점수를 바로 다시 계산하고 글은 "다시 써야 함"으로 표시 → 그 궁합을 열 때(`GET`) 다시 쓰기 시작(이때 한도는 세지 않는다 — 제안).
- S2-6 daily-cap: 계정마다 그날(한국 날짜) 새로 만든 궁합 수가 50 이상이면 429 `RATE_LIMITED`(지금 안내 그대로). 링크로 만들어진 양쪽 기록도 각자 하나로 센다(104 의 7).

1. `POST /synastry/direct` 는 요약을 받을 때까지 기다리는 동기 호출이고, 네 영역 리포트는 `POST /synastry/{id}/report` 로 따로 시작하며 상대 출생 정보를 다시 보내야 한다 → 104 의 "한 번에"는 새 비동기 흐름(S2-4). 1.0.0 앱은 궁합을 부르지 않아 바꿔도 깨질 앱은 없다(웹 스테이징 · 옛 테스트앱 빌드만 확인).
2. 상대 출생 정보를 저장하지 않는다는 것이 V7 표 주석 · 서버 결정 010 · `direction` 설명에 박혀 있다 → 서버 결정 053 에서 대체 표시하고 처리방침과 같은 날 바꾼다.
3. `Relation` 은 LOVE · FRIEND · WORK · FAMILY, DB 제약도 넷 → 입력만 막고 읽기는 남긴다.
4. `GenerationQuota` 는 분 · 시간 창의 메모리 카운터(서버 한 대 전제) → 하루 안전 한도는 DB 로 세야 블루그린 · 재시작에도 맞다.
5. 60점 아래 `scoreLabel`("다른 결의 사이")을 서버가 준다 → 104 의 3 은 표시 안 함. 서버에서 뺄지(계약 단순) · 앱이 무시할지 서버 결정 053 에서 정한다.
6. `ExpoPush` 가 모든 메시지에 `sound: default` 를 박고 채널이 없다 → 밤 무음은 메시지마다 소리 · 채널을 싣게 바꿔야 한다(S3-6), 앱은 안드로이드 `quiet` 채널을 만든다.
7. `push.Notice`(푸시 한 통의 모양)라는 이름이 이미 있다 → 공지 기능과 이름이 겹친다(S4-2).
8. `notifications.kind` 는 DB 제약으로 다섯 종류만 받는다 → 새 종류(링크 · 공지)마다 마이그레이션.
9. architecture.md 에 `POST /synastry/invites` 가 있지만 만든 적 없다("초대 · 수락은 아직") → 링크가 대신하니 지운다.
10. `EntitlementPolicy.allows` 자리가 이미 있다(402 예약) → 결제는 이 함수 안만 바꾸면 된다. 수령자 판정에는 나 탭 · 시기 풀이 표를 읽어야 해서 `report` 패키지 안에 둔다.
11. 광고 푸시는 `push_events` 의 하루 한 번 제약이 있다 → 공지 알림은 다른 길(제약 밖)로 보낸다.
