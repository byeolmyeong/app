# 020. 궁합의 관계 유형에 가족을 넣고, 태어난 시각을 모르면 태어난 곳을 묻지 않는다

> 상태: 활성 · 결정일 2026-11-11 · docs/release-1.0.0.md F1·F5 를 바꾼다. 서버 계약(`relation`, `placeId`)도 바뀐다.

## 맥락
- 궁합의 관계 유형은 연애·친구·일 세 가지였다(결정 010). 소유자가 "관계는 더 많다" 고 했고, 부모·형제·자녀 같은 가족이 빠져 있었다.
- 태어난 곳은 상승점·하우스 계산에만 쓰인다. 행성 위치는 날짜와 시각만으로 정해진다. 시각이 "모름" 이면 서버는 상승점·하우스를 계산하지 않으므로 태어난 곳을 쓰지 않는다. 쓰지 않는 값을 필수로 받고 있었다.

## 결정
1. 관계 유형은 네 가지다: 연애 · 친구 · 일 · 가족. 서버 값은 `LOVE` · `FRIEND` · `WORK` · `FAMILY`.
   - 가족의 가중치(제안): 달-달 ×2, 태양-달 ×1.5, 나머지 ×1. 정서적으로 편안한지와 서로를 돌보는 결을 본다. [확인 필요] 궁합을 만들 때 표본 차트로 분포를 보고 확정한다(다른 유형의 "합산값 → 점수 변환" 과 함께).
   - 랭킹과 궁합 리포트도 가족을 같은 방식으로 다룬다.
2. 태어난 시각이 "모름" 이면 태어난 곳을 묻지 않는다.
   - 앱: "태어난 시각을 몰라요" 를 고르면 태어난 곳 칸이 사라진다. 시각을 다시 넣으면 칸이 나타나고 그때는 필수다.
   - 서버: `POST /charts` · `PUT /profile` 의 `placeId` 는 `time` 이 `null` 일 때 없어도 된다(있어도 쓰지 않고 저장하지 않는다). `time` 이 있으면 지금처럼 필수다. `GET /profile` 은 그때 `placeId: null` 을 준다.
   - 시각을 모르는 날의 기준 시각은 지금처럼 한국 표준시 정오다(국내 출생만 받는다, F1).

## 버린 대안
- 관계 유형을 사용자가 직접 적기 — 적은 말로는 점수 가중치를 다르게 줄 수 없다. 부를 이름은 지금도 직접 적는다.
- 시각을 몰라도 태어난 곳을 받아 두기 — 나중에 시각을 알게 되면 어차피 출생 정보를 고치러 온다. 쓰지 않는 개인정보는 받지 않는다.

## 영향
- 앱: 입력 화면, 보관하는 출생 정보(`place` 가 없을 수 있다), 마이의 출생 정보 줄.
- 서버: `profiles.place_id` 가 비어 있을 수 있다(마이그레이션), 요청 검증, 해석·리포트가 출생지를 찾는 곳.
- 구현은 심층 리포트(네 영역) 작업이 끝난 뒤에 한다. 같은 파일을 고치고 있어서 겹친다.
