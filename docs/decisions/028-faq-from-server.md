# 028. 자주 묻는 질문의 글은 앱에 싣지 않고 서버에서 받는다(관리자가 고친다)

> 상태: 활성 · 결정일 2026-11-12 · 결정 024 의 "자주 묻는 질문: … 글은 `src/content/strings.ts` 에 둔다" 를 대체한다. 024 의 나머지(설정의 두 줄 · 펼치고 접는 목록 · 문의하기)는 그대로다. 번호 025 · 026 은 아직 합쳐지지 않은 다른 브랜치가 쓴다.

## 맥락
- 결정 024 는 질문과 답 열 개를 앱의 문구 파일에 실었다. 글 하나를 고치려면 앱을 다시 내야 한다.
- 소유자가 2026-11-12 에 정했다: 관리자가 관리 화면에서 자주 묻는 질문을 고치고, 앱은 그것을 보여 준다.

## 결정
- 서버 계약(서버 저장소와 함께 만든다. 이름을 바꾸지 않는다): `GET /faqs` — 세션 없이. 200 `[{ "id": string, "question": string, "answer": string }]`. 공개된 것만, 보여 줄 순서대로 온다. 빈 배열일 수 있다. 5분쯤 캐시해도 된다. 429 가 올 수 있다.
- `/settings/faq` 는 화면을 열 때 `GET /faqs` 로 받는다. 받는 동안 "불러오는 중", 실패하면 안내와 "다시 시도"(스스로 다시 부르지 않는다), 빈 목록이면 "아직 등록된 질문이 없어요" 와 문의하기로 가는 줄을 보여 준다.
- 답은 그냥 글자로 보여 준다. 줄바꿈은 그대로 살리고 HTML · 마크다운으로 해석하지 않는다.
- 앱에 실었던 질문과 답(`strings.faq.items`)은 지운다. 글의 주인은 관리 화면이다(초안 열 개는 관리 저장소에 씨앗 자료로 넘겼다. 여기에 사본을 두지 않는다). 화면의 제목 · 안내 같은 문구는 `strings.faq` 에 남는다.
- 응답은 쓰기 전에 모양을 엄격히 확인한다(배열, 항목마다 비지 않은 글자 `id` · `question` · `answer`). 하나라도 어긋나면 목록 전체를 받지 않는다(INVALID → 실패 안내).
- 받은 목록은 기기에 보관하지 않는다. 앱이 켜져 있는 동안 메모리에만 5분 두고 그동안 다시 열면 그것을 쓴다. 실패와 빈 목록은 두지 않는다.
- 가짜 서버(`EXPO_PUBLIC_USE_FIXTURES`)는 작은 예시 목록(`src/lib/fixtures/faqs.json`)을 준다.

## 버린 대안
- 앱의 글을 기본값으로 남기고 서버가 실패할 때 보여 주기 — 글이 두 곳에 있으면 관리자가 고친 것과 어긋난다. 소유자가 사본을 두지 않기로 했다.
- 기기에 보관해 오프라인에서도 보여 주기 — 고친 글이 늦게 보이고, 지운 글이 남는다. 문의하기도 어차피 연결이 있어야 한다.
- 답을 마크다운 · HTML 로 — 관리자가 넣은 글이 앱에서 코드로 해석될 길을 만들지 않는다.

## 영향
- `src/lib/api.ts`(`listFaqs` · `isFaqList`), `src/lib/fixtures/faqs.json`, `src/features/support/use-faqs.ts`(새 파일) · `faq-list.tsx`(항목의 키를 `id` 로), `src/app/settings/faq.tsx`, `src/content/strings.ts`(`faq.items` 삭제, 상태 문구 추가).
- 서버: `GET /faqs` 가 필요하다(서버 저장소에서 함께 만든다).
- 결정 024 의 "[확인 필요] 자주 묻는 질문의 첫 문안은 초안이다" 는 이제 관리 화면에서 확정한다. 앱 문구의 "건강 · 투자 · 미래 사건을 단정하지 않는다" 규칙은 관리자가 글을 쓸 때 지켜야 한다(앱은 받은 글을 그대로 보여 준다).
