## 내 결정(묻지 않고 고른 기본값 — 각 저장소의 새 결정에서 확정)
- 이 계획 파일은 앱 저장소에 둔다(1.0.0 계획과 같이). 서버 · 어드민 · 랜딩의 결정은 그 묶음을 할 때 그 저장소에 쓴다.
- 결제 확인은 서버가 RevenueCat REST(구독자 조회)로 한다. 앱의 RevenueCat 사용자 id = 계정 id. 비밀 키는 서버 환경 변수 `REVENUECAT_SECRET_KEY` 하나(이름 제안). 웹훅(환불 회수)은 101 의 [확인 필요]가 닫힌 뒤.
- **결제 시작 시각**은 서버 설정 하나(`byeolmyeong.purchase.starts-at`, 제안). 비어 있거나 아직이면 1.0.0 처럼 모두 허용하고 받기 426 도 없다. 서버 main 이 앱 출시보다 먼저 운영에 가므로(출시 순서 2 → 5), 출시일에 소유자 승인 뒤 값을 넣고 다시 배포한다(블루그린 10초).
- **1.0.0 수령자는 풀이 행으로 가리지 않고 따로 적는다**: V36 `entitlements`(계정 · 출처 `LEGACY` · `STORE`). 배포 때 지금 완성된 풀이(`detail_reports` 의 DONE)와 감사 로그 `REPORT_REQUESTED`(ME · TIMING, 1년 보관)로 채우고, 결제 시작 시각 전까지는 풀이가 완성될 때마다 `LEGACY` 를 더한다. 풀이 행은 출생 정보를 바꾸면 지워지고 만든 때 칸이 없어 근거가 못 된다(아래 "서버 코드에서 본 것" 12).
- 산 사람은 결제 직후 앱이 부르는 확인(S1-5)에서 `STORE` 로 적고, 그 뒤 판정은 표만 본다. RevenueCat 은 표에 없을 때만 묻는다(새 기기 복원 등 — 있으면 적는다).
- 마이그레이션 번호는 **합칠 때 메인이 develop 의 다음 번호로 정한다**. 서버 Flyway 에 `outOfOrder` 가 없어, 높은 번호가 먼저 합쳐지면 스테이징이 뒤에 온 낮은 번호에서 멈춘다. 줄은 계획 번호(S① V36 · S② V37 · S④ V38 · S③ V39)로 쓰되 코드 · 시험이 번호에 기대지 않게 한다.
- 궁합 하루 안전 한도는 **50**(104 의 세션 예시), 몰림 묶기는 **10분 안 3명 넘게**(104 의 예시) — 서버 설정값으로 두고 운영 로그를 보고 바꾼다.
- 궁합 하루 한도는 DB 로 센다(그날 한국 날짜에 만든 내 궁합 수). 지금 생성 한도(`GenerationQuota`)는 서버 메모리라 재시작 · 블루그린(서버 046) 때 초기화된다.
- "나왔어요" 알림의 "앱을 닫았을 때": 서버는 완성 뒤 **30초 안에 그 궁합의 결과를 받아 가지 않으면** 알림함 + 푸시를 보낸다(제안 — 앱이 화면을 떠났는지 서버가 알 길이 없어서). 받아 갔으면 보내지 않는다. 10초마다 도는 일이 조건부 update 로 한 번만 보낸다(블루그린이 겹쳐도 두 번 가지 않게).
- 밤 무음(21:00 ~ 08:00 한국 시각)은 궁합 · 공지 알림 모두에 같은 규칙: iOS 는 `sound` 를 빼고, 안드로이드는 조용한 채널(`quiet`, 1.1.0 앱이 만든다)로 보낸다. 채널이 없는 기기에 `channelId` 를 실으면 알림이 아예 안 보이므로(Expo 문서), 서버는 `push_devices` 의 플랫폼 · 앱 버전을 보고 **1.1.0 이상 안드로이드에만** `quiet` 를 싣는다.
- 랜딩은 정적 사이트(`nuxt generate`)다. 링크 미리보기 제목에 보낸 사람 닉네임이 들어가므로(104 의 8) `/i/**` 만 서버에서 그린다 — 다른 페이지는 지금처럼 미리 만들고 `/i/**` 만 Vercel 함수(랜딩 새 결정, L①).
- 링크 코드는 짧은 무작위 8자(대문자 + 숫자, 헷갈리는 글자 뺌). 주소 경로는 **`/i/{code}`**(결정 111) — 랜딩 `byeolmyeong.com/i/…` · 웹 앱 `app.byeolmyeong.com/i/…` · 앱 라우트 `/i/[code]` 모두 같다.
