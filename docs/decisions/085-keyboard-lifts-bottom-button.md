# 085. 화면 키패드가 뜨면 맨 아래 주 버튼은 키패드 바로 위(12)에 온다 — 키패드가 덮은 높이는 공용 훅 하나가 창 바닥 기준으로 재고, Screen 이 그만큼 아래를 띄운다

> 상태: 활성 · 결정일 2026-11-26(메인 — 원인 보고를 보고 방식과 결정할 것 셋을 정함) · 입력 화면들의 `KeyboardAvoidingView` 를 대체한다. 결정 042(가입 단계, 보드 7-1 "키보드가 올라오면 아래 버튼이 키보드 바로 위로")를 모든 입력 화면 · 세 플랫폼으로 넓힌다

## 맥락
- 입력 화면 네 곳(가입 단계 · 마이 닉네임 · 마이 출생 정보 · 새 문의)은 키패드 처리를 RN `KeyboardAvoidingView`(KAV)에 맡겼다. KAV 는 어느 플랫폼에서도 "창 바닥에서 키패드가 덮은 높이" 만큼 버튼을 올리지 못해 맨 아래 주 버튼이 키패드에 가렸다.
  - iOS: KAV 는 자기 자리를 onLayout(부모 기준)으로 재 `frame.y + frame.height − 키패드 위 끝` 만큼 띄운다. KAV 가 Screen 안(위 안전 영역 · 머리 아래)에 있어 `frame.y` 가 창 기준이 아니다 — 그 위 높이(마이 약 118pt · 가입 단계 약 62pt, iPhone 17 Pro)만큼 덜 올라간다.
  - 웹: react-native-web 의 KAV 는 아무것도 하지 않는 View 다. 휴대폰 브라우저의 키패드는 페이지 위를 덮고(보이는 칸 `visualViewport` 만 줄어든다) 문서의 창은 그대로라 버튼이 그대로 가린다.
  - 안드로이드: `behavior` 를 주지 않아(undefined) 아무것도 하지 않는다. edge-to-edge 창은 키패드가 떠도 줄지 않는다.
- 홈의 출생 정보 입력(`features/chart/birth-form`)은 버튼이 굴러가는 내용 맨 아래에 있어, 키패드가 뜨면 버튼이 정해진 자리에 있지 않았다.
- 키패드가 떠 있을 때 버튼과 키패드 사이가 가입 단계(보드 7-1)는 12, 마이 화면들은 바닥 여백 34 그대로로 서로 달랐다.

## 결정
1. **키패드가 덮은 높이는 공용 훅 하나가 잰다** — `src/components/use-keyboard-height`(앱 `.ts` · 웹 `.web.ts`). 창 바닥에서 키패드가 덮은 높이, 떠 있지 않으면 0.
   - iOS: 키패드가 움직이기 시작할 때(`keyboardWillChangeFrame`) 끝 자리로 `창 높이 − 키패드 위 끝(screenY)`. 화면 칸이 키패드와 같은 시간 · 곡선으로 움직이게 LayoutAnimation 을 건다. `keyboardWillHide` 면 0.
   - 안드로이드: `keyboardDidShow` 의 높이 + 아래 안전 영역. RN 이 높이에서 아래 시스템 막대를 빼고 주기 때문이다(`ReactRootView.checkForKeyboardEvents` 의 `ime.bottom − systemBars.bottom`). `keyboardDidHide` 면 0.
   - 웹: `visualViewport` 가 바뀔 때마다(resize · scroll) `문서 창 높이(clientHeight) − (보이는 칸 위 끝 pageTop + 높이)`. 손가락으로 확대한 동안(scale ≠ 1)은 키패드가 아니라 0. 외부 주소 · 스크립트를 쓰지 않아 CSP(결정 077)는 그대로다.
   - 화면이 여럿 쌓여도 키패드 알림 구독은 모듈 한 곳에 하나이고, 구독하는 화면이 없으면 끊는다. 다시 구독할 때 키패드가 떠 있으면 그 자리에서 시작한다.
2. **`Screen` 의 `avoidKeyboard` 를 켠 화면은 키패드가 떠 있는 동안 아래 안전 영역(또는 `bottomInset`) 대신 키패드가 덮은 높이만큼 아래를 띄운다.** Screen 이 창 바닥까지 닿는다고 본다(화면 쌓기의 화면은 모두 그렇다). 아래 시트(RN Modal) 안의 입력은 이 규칙 밖이다.
3. **키패드가 떠 있을 때 맨 아래 주 버튼과 키패드 사이는 모든 입력 화면에서 12** — `Sizes.keyboardGap`(가입 단계 · 보드 7-1 의 값, `StepLayout.keyboardGap` 을 옮긴다). 버튼 칸이 그 여백을 둔다. 키패드가 내려가면 각 화면의 지금 바닥 여백 그대로다(가입 단계 34 · 마이 화면들 안전 영역 + 34 · 출생 정보 입력 안전 영역 + 24).
4. **입력 화면은 KAV 를 쓰지 않는다.** 가입 단계 · 마이 닉네임 · 마이 출생 정보 · 새 문의 · 출생 정보 입력(홈 · `/birth`)이 `avoidKeyboard` 로 바뀐다. 가입 단계가 따로 갖던 "키패드가 떠 있는가"(웹은 언제나 아니라고 봤다)도 이 훅으로 합친다.
5. **출생 정보 입력의 버튼은 맨 아래 고정 칸에 둔다** — 마이 출생 정보와 같은 짜임("주 버튼은 늘 맨 아래 같은 자리"). 위 제목 · 안내와 세 칸만 굴러가고, 서버가 거절한 안내는 고정 칸 안 버튼 바로 위에 둔다.

## 근거
- 창 바닥을 기준으로 재므로 KAV 처럼 화면 머리 · 안전 영역 높이에 따라 어긋나지 않는다.
- 새 네이티브 의존성이 없다. `react-native-keyboard-controller` 는 고친 뒤 개발 빌드를 다시 해야 하고, 웹은 어차피 `visualViewport` 로 따로 재야 한다.
- 버튼과 키패드 사이를 한 값으로 두면 입력 화면마다 키패드 위 모양이 같다.

## 결과·재검토 조건
- 앱은 JS 만 바뀌지만 expo-updates 가 없어 iOS 에는 새 빌드로 나간다.
- 안드로이드는 RN 코드로 확인했고 기기 화면은 찍지 않았다. 기기에서 버튼이 시스템 막대만큼 어긋나면 1 의 안드로이드 계산을 다시 본다.
- 시트(Modal) 안의 입력이 키패드에 가리면 그 시트에 같은 훅을 쓴다. iPad 의 떠 있는 키패드처럼 창 바닥에 붙지 않는 키패드는 다루지 않는다.
