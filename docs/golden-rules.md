# Golden Rules — 위반 금지

> 상태: 활성 · 기준 2026-11-10 · 마스터 출처 `agent-ready-kit/skills/second-brain/templates/GOLDEN_RULES.md`

모든 프로젝트에 공통인 규칙이다. 프로젝트는 이 파일을 복사해 "프로젝트 규칙" 절에 자기 규칙을 덧붙인다. 공통 규칙은 지우지 않는다. 해당 없으면 규칙 뒤에 "해당 없음: 이유"를 적는다. 각 규칙은 한 줄 규칙 + 한 줄 이유다. 사고 배경은 `docs/engineering-lessons.md`에 두고 여기서는 경로만 가리킨다.

특정 파일을 만질 때만 필요한 규칙은 여기 적지 않고 `.claude/rules/<주제>.md`에 `paths:` glob과 함께 둔다(외부 API·결제·발송 / 멀티테넌트 권한 / 웹 백엔드 공통이 기본 제공). 이 파일은 항상 로드되므로 "항상 필요한가?"에 예인 규칙만 남긴다.

## 브랜치·커밋
- 보호 브랜치(`main`·`master`·`develop`)에 직접 쓰지 않는다. 작업 브랜치 → PR. 이유: 되돌릴 수 없는 변경이 리뷰 없이 들어간다. 시스템 차단: `.claude/hooks/guard.sh`.
- 한 커밋 = 한 관심사. 버그 수정에 리팩터·포맷·정책 변경을 섞지 않는다. 이유: 되돌릴 때 같이 사라진다.
- 지침·스킬·워크플로우 문서 변경은 도메인 `feat` 커밋에 끼워 넣지 않는다. 별도 `chore`/`docs`. 이유: 규칙 변경이 기능 커밋 뒤에 숨는다.
- 파괴적 변경(스키마 `DROP`·컬럼 삭제·공용 API 제거)과 신규 공용 helper는 `chore: 정리`류 커밋에 넣지 않는다. 제목에 명시. 이유: 리뷰어가 못 본다.
- 기준 브랜치를 작업 브랜치에 병합한 뒤의 정리 커밋은 방금 병합된 타인의 변경을 되돌리지 않았는지 diff로 확인한다.

## 비밀값·로그
- 비밀값(키·비밀번호·테스트 계정)은 어떤 문서·SKILL.md·로그에도 적지 않는다. 환경 변수 이름만 적는다. 시스템 차단: `.claude/settings.json`의 `Read(.env)` deny.
- 로그는 구조화 이벤트(`event` 식별자 + 필드)로 남긴다. 사용자 입력·토큰을 통째로 로그에 넣지 않는다.

## 코드 구조
- 모듈 디렉터리 레이아웃은 ADR 표준 하나만 쓴다. 비어 있는 계층 디렉터리와 단일 구현 인터페이스는 만들지 않는다.
- helper는 엣지케이스·정책명·테스트 셋 다 있을 때만 추출한다. 신설 전 helper 위치 전부를 grep하고, 같은 관심사가 둘 이상이면 가장 엄격한 쪽으로 즉시 통합한다.
- 외부 입력(요청 본문·외부 API 응답·파일)은 구조분해 전에 방어 검증한다(타입·필드 존재·빈 값 조기 반환).

## 코딩 규율
- 요청한 것만 만든다. 요청 안 한 기능·1회용 추상화·일어나지 않을 에러 처리·"혹시 몰라서" 옵션은 넣지 않는다. 이유: 줄 하나하나가 리뷰·유지·탐색 비용이다. 30줄이 될 일이 10줄이면 10줄이 맞다.
- 외과적으로 고친다. 요청과 직접 연결된 줄만 바꾸고 인접 코드를 "개선"하지 않는다(포맷·이름·구조). 이유: diff 에 요청 밖 변경이 섞이면 리뷰어가 진짜 변경을 못 보고, 되돌릴 때 같이 사라진다.
- 구현 전에 가정을 적는다. 모호하면 해석을 둘 다 보여주고 묻거나(`AskUserQuestion`), 급하면 가정을 명시하고 더 단순한 쪽으로 간다. 이유: 틀린 가정 위의 완성품은 처음부터 다시다.

## 문서·결정
- 구조·정책 결정이 바뀌면 코드보다 먼저 `docs/decisions/`에 새 ADR을 쓴다. 기존 ADR은 대체 표시만 하고 고쳐 쓰지 않는다.
- 회의록·스레드·export 원본은 `docs/raw/`에 그대로 두고 정리본이 원본을 경로로 가리킨다. 원본은 고치지 않는다. 이유: 원본이 바뀌면 정리본의 근거가 사라진다.
- 두 문서 이상을 읽고 종합한 답은 `docs/synthesis/<주제>.md`에 남기고 읽은 문서에서 경로로 가리킨다. 한 문서만 읽은 답은 저장하지 않는다. 이유: 같은 고민을 6개월마다 처음부터 하면 지식이 누적되지 않는다.
- 변동 가능한 외부 수치(호출 한도·요금)는 문서 한 곳만 단일 출처로 두고 다른 문서는 절 제목을 참조한다.
- 자동 리뷰·브리핑의 지적은 코드로 사실 확인한 뒤에만 작업으로 만든다. 오탐은 사유만 남긴다.
- 구조·명령·규칙이 바뀌면 같은 PR에서 CLAUDE.md·docs를 갱신한다. 이유: 맥락이 코드보다 늦으면 agent는 옛 세계에서 일한다.

## 되돌리기·자율성
- 작업은 작업 브랜치(또는 git worktree)에서 한다. 망쳐도 main은 멀쩡하고, 마음에 안 들면 버린다. 이유: 되돌릴 수 있어야 자율성을 줄 수 있다.
- 삭제·이동·일괄 변경은 먼저 대상 목록을 출력(dry-run)하고 승인 후 실행한다. 이유: "지울 목록"이 보이면 실수가 실행 전에 잡힌다.
- 되돌리기 어려운 작업(배포·publish·merge·메일 발송·DB 파괴적 변경)은 사람이 한 번 확인한다. 시스템: `.claude/settings.json`의 `permissions.ask`.
- 정말 안 되는 것만 막는다. 나머지는 자유도를 준다. 이유: 규칙이 늘기만 하는 하네스는 실패 신호다.
- 검증은 만든 쪽이 하지 않는다. 측정(`/verify`)과 리뷰(`reviewer` 에이전트, 다른 컨텍스트)를 분리한다. 이유: 같은 맥락에 갇히면 같은 실수를 못 본다.

## 검증·증거
- 완료·통과·고쳤다고 말하기 전에 그 명령을 **이번에** 돌리고 출력을 본다. "아마"·"될 것"은 결과가 아니다. 서브에이전트의 "성공" 보고는 diff·테스트로 확인한다. 이유: 증거 없는 완료 주장은 거짓말과 구분되지 않는다.
- 새 동작·버그 수정은 실패하는 테스트를 먼저 보고 구현한다(red → green). 통과만 하는 테스트는 테스트가 아니다. 이유: 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다.
- 버그는 원인부터: 에러 전문 읽기 → 재현 → 최근 변경 → 가설 하나 → 최소 수정 하나. 증상만 덮지 않는다. 세 번 고쳐도 안 되면 구조 문제로 보고 멈춘다. 이유: 추측 수정은 느리고 새 버그를 만든다.
- 기준을 낮춰 통과시키지 않는다(테스트 skip·assert 완화·임계 하향·타임아웃 연장). 기준 변경은 사용자 승인. 시스템: `.claude/skills/verify/SKILL.md` 표.

## 개선 루프
- 같은 작업을 3번 반복하면 스킬로, 같은 실수를 3번 하면 규칙으로 만든다. 안 쓰는 스킬·MCP·규칙은 바로 지운다. 이유: 하네스는 시간이 갈수록 단순해져야 정상이다. 관측은 `/retro`.

## 프로젝트 규칙
- 차트·별자리·하우스·변곡점 구간·궁합 점수를 앱에서 계산하지 않고 서버가 준 값만 그린다. 이유: 계산을 두 언어에 두면 결과가 어긋난다. 근거 docs/decisions/006-server-side-chart.md
- 시각 "모름"인 차트에는 하우스·상승궁을 보여 주지 않는다. 이유: 계산할 수 없는 값이다.
- 로그인 여부·만 14세 여부(1.1.0 부터 구매 여부)를 앱의 값으로 판정하지 않는다. 서버 응답을 따른다. 이유: 앱의 값은 고칠 수 있다.
- 문구에 건강·투자·미래 사건의 단정을 쓰지 않는다. 궁합 점수는 서버가 계산한 값만 보여 주고 앱에서 만들지 않는다. 이유: 제품 규칙과 스토어 심사·법적 위험, 점수 조작 방지. 근거 docs/release-1.0.0.md, docs/decisions/010-synastry-score-ranking-share-cards.md
- 색·글자·간격은 `src/constants/theme.ts`, 문구는 `src/content/strings.ts` 에서만 가져온다. 이유: 디자인 기준과 번역이 한 곳에서 바뀌어야 한다.
- 출생 정보(생년월일·시각·장소)를 로그·공유 페이지·분석 이벤트에 남기지 않는다. 이유: 개인정보다.
