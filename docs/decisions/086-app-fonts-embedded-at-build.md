# 086. 앱(iOS · 안드로이드) 글꼴은 빌드 때 넣는다(expo-font 설정 플러그인) — 파일은 공식 OTF 셋 그대로, 덮는 글자도 그대로

> 상태: 활성 · 결정일 2026-11-26 · 성능 계획(docs/plans/2026-11-21-app-perf.md)의 "다음 후보 1 — 앱 글꼴 4.74MB" · 결정 033 의 "Pretendard 하나, 굵기 400 · 500 · 600" 은 그대로 · 웹 글꼴(성능 계획 1, `scripts/pretendard-web.py`)은 그대로 · 테스트앱 빌드 14 부터

## 맥락
- 앱은 Pretendard 1.3.9 공식 OTF 셋(Regular 1,574,352B · Medium 1,584,068B · SemiBold 1,583,704B = 4,742,124B)을 JS 에셋으로 싣고, 실행 때 `useFonts` 로 등록했다. 스플래시는 이 등록이 끝나기를 기다렸다.
- 실행 때 등록이 하는 일(코드로 확인 — expo-asset 58.0.21 · expo-font 58.0.12, expo-updates 없음):
  - **안드로이드(릴리스)**: JS 에셋은 APK 의 `res/raw` 에 압축되어 있어, 처음 실행 때 셋을 풀어 캐시 폴더로 복사한다(4.74MB 쓰기). 그 뒤로는 실행마다 복사본 셋을 통째로 읽어 MD5 를 맞춘 뒤 등록한다. 기기에는 APK 안 압축본(약 3.17MB)과 캐시 복사본(4.74MB) 두 벌이 남는다.
  - **안드로이드 9(API 28) 이하**: 실행 때 등록은 가족의 기본 굵기 하나만 올려(expo-font `FontLoaderModule.familyTypeface`) 500 · 600 이 400 이나 흉내 낸 굵게로 보인다.
  - **iOS**: 앱 묶음 안의 파일을 그 자리에서 등록한다(복사 없음). JS → 네이티브 왕복과 파일 셋 등록(이 맥의 CoreText 로 파일마다 6~12ms)을 스플래시가 기다린다.
- expo-font 문서(SDK 58)는 iOS · 안드로이드에서 설정 플러그인을 권하고 "`useFonts` 는 설정 플러그인을 쓸 수 없을 때만" 쓰라고 한다. 설정 플러그인으로 넣은 글꼴은 앱이 뜰 때 이미 있다.
- 글꼴은 AI 풀이 글 · 사용자가 지은 닉네임 · 관리자가 쓴 FAQ · 문의 답변을 그린다. 현대 한글 11,172자 중 어떤 글자든 나올 수 있다.

## 결정
1. **앱 글꼴은 expo-font 설정 플러그인(app.json)으로 빌드 때 넣는다.** iOS 는 `UIAppFonts`(가족 이름은 파일 안의 이름 "Pretendard" — 셋 다 같다), 안드로이드는 `res/font` 의 XML 가족 "Pretendard"(굵기 400 · 500 · 600, theme.ts `FontFamily` · `FontWeight` 와 같다). 실행 때 `useFonts` 등록은 하지 않고, 스플래시는 글꼴을 기다리지 않는다.
2. **파일은 공식 배포 그대로** — `pretendard@1.3.9` 의 `dist/public/static/Pretendard-{Regular,Medium,SemiBold}.otf`(`assets/fonts/`, 라이선스 `Pretendard-LICENSE.txt` 함께). 고치지 않는다(OFL Reserved Font Name "Pretendard").
3. **덮는 글자는 그대로**: 현대 한글 11,172자 전부(KS X 1001 2,350자 포함) · 라틴 · 그리스 · 키릴 · 기호 — 코드 포인트 14,336개, 앱 문구(`src/content`)의 글자 642개 모두. 한자 · 이모지는 원래 없어 시스템 글꼴이 그린다(폴백, 앞뒤 같음).
4. **웹은 그대로** — 공식 부분 글꼴 woff2(`use-app-fonts.web.ts` · `web-fonts.ts`).
5. **개발 빌드**: 이 결정 전에 만든 개발 빌드(development client)에는 글꼴이 없어 시스템 글꼴로 보인다. 개발 빌드를 다시 만든다(Expo Go 는 원래 쓰지 않는다, 결정 034).

## 근거
- 글꼴 파일을 줄이는 안(C · D · E · F)은 저마다 첫 실행 비용 · 덮는 글자 · 글꼴 이름 중 하나를 잃는다. 파일은 그대로 두는 게 낫다.
- 들이는 방식을 바꾸면(B) 파일과 글자는 그대로이면서, 안드로이드 기기 저장 4.74MB · 처음 실행 복사 · 실행마다 읽기와 MD5 · 스플래시의 글꼴 기다림이 없어지고, 안드로이드 9 에서 굵기 셋이 제대로 보인다. 플랫폼이 권하는 방식이다.

## 결과·재검토 조건
- 앱 묶음의 글꼴 바이트는 그대로다(4.74MB). JS 에셋에서 빠지고 네이티브 프로젝트(iOS 앱 묶음 · 안드로이드 `res/font`)로 옮겨 간다.
- 안드로이드 API 24~27 은 RN 이 굵기 700 미만을 보통 굵기로 고르는 것이 앞뒤 같다(500 · 600 이 400 으로).
- 확인(2026-11-26): iOS 시뮬레이터(iOS 26.3, Release 빌드)에서 OTF 셋이 앱 묶음 맨 위에 한 벌씩만 실리고(`assets/` 에는 없음) `UIAppFonts` 로 등록되며(Pretendard-Regular · Medium · SemiBold), 굵기 셋 · 드문 글자(똠 · 쀍 · 휑 · 갉 · 녘)가 Pretendard 로, 한자는 시스템 글꼴로 그려졌다 — 실행 때 등록한 옛 방식과 폴백이 같다. 안드로이드는 이 맥에서 빌드하지 않았다(prebuild 결과의 `res/font` XML · `ReactFontManager` 등록만 확인) — 안드로이드를 내기 전에 기기에서 굵기 셋을 본다.
- 앱 크기를 더 줄여야 하면, 닉네임 · 풀이 글 · 답변의 글자 분포 자료를 모아 D 를, 또는 이름을 바꾸는 E 를 다시 본다.
