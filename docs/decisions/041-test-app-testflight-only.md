# 041. 같은 코드로 테스트앱(스테이징, TestFlight 전용)과 운영앱을 따로 만든다

> 상태: 활성 · 결정일 2026-11-19 · 계획: docs/plans/2026-11-19-testflight-test-app.md · 출처: 소유자 대화(2026-11-19)

## 맥락
- 서버와 웹은 스테이징과 운영으로 나뉘어 있다(결정 037, 서버 결정 020). 폰 앱은 하나뿐이라 폰에서 스테이징을 확인할 방법이 없었다.
- 소유자 · 팀 · 테스터가 스테이징을 폰에서 보고, 운영앱과 한 폰에 같이 깔아 둘 수 있어야 한다(소유자 2026-11-19).
- 소셜 로그인은 공급자마다 앱을 번들 ID 로 등록한다(결정 034). 번들 ID 가 하나 더 생기면 구글 · 애플 · 카카오 설정도 따라간다.
- 서버는 토큰의 대상(aud)을 환경 변수로 받는다. 애플 코드 교환 · 탈퇴 철회는 `.p8` 키 하나로 하고, 그 키는 자기 그룹(primary App ID)의 client_id 에만 쓰인다.

## 결정
1. **앱 둘**(같은 코드, 빌드 때 `APP_VARIANT` 로 고른다)

   | | 테스트앱 | 운영앱 |
   |---|---|---|
   | 이름(홈 화면 · App Store Connect) | 별명 테스트 | 별명 |
   | 번들 ID(= 안드로이드 패키지) | `com.byeolmyeong.app.test` | `com.byeolmyeong.app` |
   | scheme | `byeolmyeong-test` | `byeolmyeong` |
   | 서버 | `api-staging.byeolmyeong.com` | `api.byeolmyeong.com` |
   | 웹(공유 링크) | `app.staging.byeolmyeong.com` | `app.byeolmyeong.com` |
   | 카카오 앱 | 테스트 카카오 앱 "별명 개발" | 운영 카카오 앱 "별명" |
   | EAS 빌드 프로필 / EAS 환경 | `test` / `preview` | `production` / `production` |
   | `APP_VARIANT` | `test` | 없음(= 운영) |
   | 올리는 곳 | TestFlight 에만 | TestFlight → App Store |

2. **`APP_VARIANT`**: 없음 · 빈 값 · `production` 은 운영 설정 그대로다(웹 · 개발 빌드가 바뀌지 않는다). `test` 는 위 표의 테스트앱 값. 그 밖의 값은 `app.config.ts` 가 에러를 낸다 — 오타 하나로 스테이징을 보는 빌드가 운영 번들 ID 로 올라가지 않게.
3. **개발 빌드**(`development` · `development-simulator`)는 운영 번들 ID 를 그대로 쓴다. 공급자 콘솔의 운영 등록(구글 "별명 iOS", 운영 카카오 앱의 iOS 번들 ID)으로 기기 로그인을 확인한다. 로컬 개발도 운영 카카오 앱을 쓴다(localhost 리디렉트가 거기 있다).
4. **"TestFlight 에만" 은 운영 규칙으로 지킨다.** 막는 설정은 없다. App Store Connect 에서 테스트앱을 심사에 제출하지 않는다.
5. **공급자 설정**
   - 구글: Google Cloud 프로젝트 `byeolmyeong` 하나에 웹 클라이언트 하나(두 서버의 aud, 두 웹), iOS 클라이언트 둘("별명 테스트 iOS" · "별명 iOS"). 앱은 웹 클라이언트 ID 로 ID 토큰을 받으므로 iOS 클라이언트는 같은 프로젝트에 있어야 한다.
   - 애플: 테스트 App ID 의 Sign in with Apple 은 **운영 `com.byeolmyeong.app` 그룹에 묶는다**(Group with an existing primary App ID). 서버의 애플 키 하나로 두 앱의 코드 교환 · 탈퇴 철회를 한다. 스테이징 서버의 `APPLE_CLIENT_IDS` 에 테스트 번들 ID 를 더한다.
   - 카카오: 스테이징(서버 · 웹 · 테스트앱)은 테스트 카카오 앱, 운영(서버 · 웹 · 운영앱)과 로컬 · 개발 빌드는 운영 카카오 앱. 두 앱 모두 이메일 필수 동의(비즈 앱).
6. **앱의 서버 · 웹 주소와 공급자 값**은 EAS 환경 변수(`preview` = 테스트앱, `production` = 운영앱)에서 받는다. 이름은 `.env.example` 과 같다. 개발용 값(`EXPO_PUBLIC_DEV_SESSION` · `EXPO_PUBLIC_USE_FIXTURES`)은 어느 EAS 환경에도 두지 않는다.

## 근거
- 번들 ID 가 다르면 두 앱이 한 폰에 같이 깔리고, 스토어 · 공급자 콘솔에서 운영 기록과 섞이지 않는다.
- 앱 동작은 이미 서버 주소 환경 변수로 갈린다. 변형이 바꾸는 것은 이름 · 번들 ID · scheme 뿐이라 코드(`src/`)는 그대로다.
- 스테이징 카카오를 테스트 앱으로 옮기면 운영 카카오 앱이 운영 전용이 되고, 스테이징 시험이 운영 앱의 사용자 · 통계에 섞이지 않는다.
- 애플 그룹으로 묶으면 서버 설정(키 하나)을 바꾸지 않아도 테스트앱의 탈퇴 철회가 된다.

## 대안
- 앱 하나 + 앱 안의 서버 전환 — 운영앱에 스테이징 주소와 전환 화면이 들어간다. 스토어 심사 · 실수 위험.
- 카카오 앱 하나 공유 — 운영 카카오 앱에 테스트 번들 ID 와 스테이징 주소가 섞인다. 소유자가 따로 만들기를 골랐다.
- 개발 변형까지 세 변형 — 개발 빌드와 운영앱이 한 폰에서 덮어쓰는 일이 실제로 생길 때 한다.
- 테스트 App ID 를 별도 primary 로 — 서버에 애플 키를 하나 더 둘 자리가 없고, 묶지 않으면 탈퇴 철회가 조용히 빠진다.

## 결과·재검토 조건
- 스테이징을 테스트 카카오 앱으로 옮겨 카카오 사용자 번호가 바뀌었다. 스테이징에서 운영 카카오 앱으로 가입했던 계정은 새 계정으로 잡힌다(스테이징 데이터라 받아들인다).
- 구글 동의 화면은 브랜드 인증 전까지 앱 이름 · 로고 없이 도메인만 보인다(외부 · 게시 앱). 출시 전에 브랜드 인증을 받는다.
- 안드로이드: 구글 안드로이드 클라이언트(서명 SHA-1) · 카카오 키 해시는 첫 안드로이드 빌드 뒤 운영 안드로이드 계획에서 한다. 테스트앱은 안드로이드로 올리지 않지만, 실수로 빌드해도 운영 패키지로 플레이에 가지 않게 패키지도 바꾼다.
- 개발 빌드와 운영앱이 한 폰에서 서로를 덮어써 불편해지면 개발 변형을 더한다.
- App Store Connect 앱 기록과 번들 ID 등록은 되돌릴 수 없다(앱을 지워도 번들 ID 는 팀에 남는다).
