# 068. 가입 중간에 나간 사람은 가입권 수명 동안 하던 단계부터 잇고, 스플래시는 홈의 첫 데이터까지 · 공유 페이지에는 없고, 웹이 서버에 닿지 못하면 로그인으로 보내지 않는다

> 상태: 활성 · 결정일 2026-11-20(소유자 "넣어 줘" · "스플래시 → 바로 홈" · 공유 링크 스플래시 "안 보이게 해") · 2 는 결정 074 가 "홈 카드의 첫 상태까지" 로 넓힌다 · 결정 042 · 044 의 "가입 초안은 메모리에만" 을 대체한다(출생 정보는 그대로 기기에 두지 않는다) · 결정 067 의 3(스플래시 걷는 때)을 넓힌다 · 계획: docs/plans/2026-11-20-resume-and-splash.md

## 맥락
- 가입 초안(약관 동의 · 닉네임 · 프로필)과 가입권(30분 · 1회용)은 메모리에만 있어(결정 042 · 044), 웹 새로 고침이나 앱을 껐다 켜면 처음부터 로그인해야 했다.
- 결정 034 의 "앱 코드가 웹에서 토큰을 만지지 않는다" 는 **세션 토큰**(로그인 상태) 이야기다. 가입권은 30분짜리 1회용 표인데, 그 표로 `POST /auth/signup` 을 부르면 서버가 계정과 세션을 함께 만든다(`cookie: false` 면 세션 토큰을 본문으로 준다). 그래서 웹 sessionStorage 의 가입권도 세션에 준하는 값이다 — 아래 "위험과 막는 것".
- 홈은 세션이 살아 있는데 기기에 출생 정보가 없으면(새 브라우저 · 다시 깐 앱) 스플래시가 걷힌 뒤 "불러오는 중이에요" 를 보였다가 홈으로 바뀌었다.
- 공유 페이지(`/s/…`)는 세션을 확인하지 않는데도 스플래시가 0.8초 보였다.
- 웹은 시작할 때 `GET /auth/session` 이 401 이 아니라 닿지 못한 것이어도 로그인 화면으로 보냈다. 앱(iOS · 안드로이드)은 이미 "닿지 못하면 보관한 토큰을 믿는다".

## 결정
1. **가입 이어 하기.** 가입권 · 그 공급자 · 적던 값(약관 버전 · 푸시 · 마케팅 동의 · 닉네임 · 프로필 번호) · 지금 단계(약관 · 닉네임 · 출생 정보) · 가입권을 받은 시각을 기기에 둔다. 앱은 세션 토큰과 같은 보안 저장소(expo-secure-store), 웹은 sessionStorage(그 탭에만, 탭을 닫으면 사라진다).
   - **가입권 수명(받은 때부터 30분과 서버 로그인 응답의 `expiresAt` 중 이른 쪽)만큼만** 둔다. 지났거나 서버가 `SIGNUP_EXPIRED` 를 주면 지우고 로그인부터.
   - 켤 때는 살아 있는 세션(앱 보관 토큰 · 웹 쿠키 세션)이 먼저다. 세션이 살아 있으면 남은 가입권을 지우고, 없을 때만 잇는다(가입 뒤 지우지 못했거나 재설치 30분 안이어도 세션을 잃지 않게).
   - 이어 한 단계는 쌓기에 그 화면 하나라 뒤로는 앞 단계로 바꿔 간다(출생 정보 → 닉네임 → 약관, 약관의 뒤로는 그만둠).
   - **출생 정보는 두지 않는다**(결정 042 · 044 그대로). 출생 정보 단계에서 나갔으면 그 단계의 빈 칸부터 다시 적는다.
   - 돌아오면 스플래시 → 하던 단계부터.
   - 가입을 마치거나 · 로그아웃 · 어떤 새 로그인이든 · 가입을 그만두면(약관 단계에서 뒤로) 바로 지운다.
2. **스플래시는 홈의 첫 데이터까지.** 처음 열어 홈으로 갈 때는 기기 저장소 읽기와(기기에 없으면) 서버에서 되살리기가 끝날 때까지 스플래시를 둔다. 10초가 넘으면 걷고 홈은 결정 065 의 규칙대로 불러오지 못한 화면(19)을 보인다. 처음 한 번만이고 탭 이동 · 돌아오기에는 걸리지 않는다.
3. **공유 페이지에는 스플래시가 없다.** 첫 프레임부터 공유 화면이다(웹은 서버가 그린 HTML 에도 스플래시를 넣지 않는다).
4. **웹이 시작할 때 서버에 닿지 못하면(401 이 아니면) 로그인으로 보내지 않는다.** 세션은 "확인하지 못함(offline)" 으로 두고 가드는 보내지 않는다. 홈은 이 기기에 받아 둔 출생 정보가 있으면 홈 + 연결 끊김 띠(20), 없으면 볼 게 없는 화면(20-1 "다시 시도")을 보인다. 30초마다와 "다시 시도" 를 누르면 다시 확인하고, 그때 서버가 401 을 주면 로그인으로. 가입 주소로 열렸는데 이어 할 가입권이 없으면 가입 단계 대신 20-1(가입은 서버 없이 나아갈 수 없다). 판정 순서: 살아 있음 → 로그인 · 403 `ACCOUNT_SUSPENDED` → 로그인(정지 화면은 문이 보낸다) · 401 → 로그인 전 · 그 밖(닿지 못함 · 5xx) → offline.
   - golden rules 의 "로그인 여부를 앱의 값으로 판정하지 않는다" 와 어긋나지 않는다: 앱은 로그인했다고 정하지 않고(계정 · 서버 데이터를 부르지 않는다), 로그인 안 했다고도 정하지 않는다. 판정은 다음 서버 응답(다시 확인 · 어느 요청의 401)이 한다.
5. (뺌) 웹 구글 버튼의 화면 읽기 · 최근 로그인은 웹 구글을 리디렉트로 바꾸는 결정 070 이 다룬다.
6. **닉네임 중복은 치기를 멈추면 묻는다.** 가입 닉네임 단계에서 규칙에 맞는 닉네임을 치고 0.5초 멈추면 `POST /auth/nickname-check` 를 한 번 부르고, 쓸 수 있으면 안내 줄에 초록(`Colors.success`) "사용할 수 있는 닉네임이에요", 겹치면 빨강 "이미 쓰고 있는 닉네임이에요"(다음 꺼짐), 확인하는 동안 다음은 흐리다. 쓸 수 있다고 확인한 이름이면 다음에서 다시 묻지 않는다(가입 때 서버가 다시 판정한다 — 409 면 닉네임 단계로). 결정 042 의 3 "다음을 누를 때 한 번" 을 대체한다. 초록 글자는 DESIGN.md 원칙 1(상태 색은 작은 아이콘만)의 예외로 이 안내 한 줄에만 쓴다. 마이의 닉네임 바꾸기는 로그인한 사람의 확인 경로가 서버에 없어(가입권으로만 묻는다) 지금처럼 저장할 때 409 로 안내한다.
7. **웹 가입 단계 사이도 앱처럼 움직이고 빈 화면이 없다.** 운영 웹은 화면 조각을 나누지 않는다(`app.json` 의 expo-router `asyncRoutes.web` = `"development"` — 누를 때 조각을 받는 동안의 빈 화면이 원인이었다). 다음 단계는 오른쪽에서 밀려 들어오고 뒤로는 오른쪽으로 나간다(웹은 앞 화면을 남기는 transparentModal 위에서 화면이 스스로 — 앱은 화면 쌓기 기본). 가려진 아래 화면은 inert. 동작 줄이기면 움직이지 않는다. 화면 조각을 못 불러오는 일이 생기면(배포가 바뀐 뒤 열린 탭) 한 번만 새로 고친다.

## 근거
- 가입권이 살아 있는 동안 다시 로그인시키면 공급자 창을 한 번 더 지나야 하고, 그사이 적은 닉네임을 잃는다. 수명이 30분이라 기기에 남는 시간도 짧다.
- 출생 정보는 가장 민감한 값이라 끝까지 메모리 밖에 두지 않는다.
- 스플래시 → 불러오는 중 → 홈의 두 번 바뀜이 스플래시 하나로 줄어든다.
- 서버가 잠깐 닿지 않는 것 때문에 로그아웃된 것처럼 보이면 다시 로그인하려다 다른 공급자로 새 계정을 만들 수 있다.

## 대안
- 가입 초안을 메모리에만(결정 042 · 044) — 소유자가 이어 하기를 골랐다.
- 웹도 localStorage — 탭을 닫아도 남아 공유 기기에 가입권 · 닉네임이 오래 남는다.
- 출생 정보까지 두기 — 개인정보라 두지 않는다.
- 닉네임을 칠 때마다 묻기 — 요청이 늘고 남의 닉네임을 떠보기 쉽다(결정 042 의 근거). 0.5초 멈춤 뒤 한 번이면 이름 하나에 한 번이고, 서버의 속도 제한(로그인 · 가입과 합쳐 주소별 분당 30)이 막는다.
- 웹이 닿지 못하면 지금처럼 로그인으로 — 위 근거.

## 결과·재검토 조건
- 가입권 수명이 서버에서 바뀌면 앱의 30분도 같이 바꾼다(`features/auth/signup-resume.ts`).
- 웹 sessionStorage 는 그 탭에만 있다: 새 탭(주소를 새로 엶)은 처음부터다. 탭 복제는 sessionStorage 를 복사하므로 두 탭이 같은 가입권을 갖지만, 가입권은 1회용이라 먼저 마친 쪽만 되고 다른 쪽은 `SIGNUP_EXPIRED` 로 로그인부터다.
- **운영 웹 한 묶음(7)의 비용 — 첫 로드**(리뷰어 측정, gzip -6): `/` 545.4KB → 608.4KB(약 +63KB, +12%), `/s/[shareId]` 542.6KB → 608.4KB. 모든 조각을 합친 전체는 638KB → 608KB 로 준다. 대신 화면을 옮길 때 받는 것이 없다.
- **개인정보**: 웹이 서버에 닿지 못하면(4) 세션 근거 없이 기기(웹은 localStorage)의 출생 정보 · 받은 풀이로 홈을 그린다. 공유 브라우저에서 앞사람이 로그아웃하지 않았다면 서버가 꺼진 동안 그 사람의 홈이 보인다 — 로그아웃은 기기 저장을 비우므로(결정 034) 로그아웃한 경우에는 없다.

## 위험과 막는 것(웹 가입권) — **받아들일 위험인지 소유자 확인 필요**
- 소유자 승인 2026-11-20 — 받아들인다(1회용 · 30분). 출시 전 보안 점검에서 웹 CSP(스크립트 출처 제한)를 건다.
- 위험: 페이지에 끼어든 스크립트(XSS)가 sessionStorage 의 가입권을 읽으면, 가입권이 살아 있는 동안(많아야 30분) 피해자의 소셜 신원(공급자 계정)에 묶인 별명 계정을 공격자가 만들고 그 세션을 가질 수 있다(`cookie: false` 로 가입하면 세션 토큰이 본문으로 온다).
- 막는 것: 가입권은 1회용이고 30분(또는 서버 만료)이면 끝난다. 가입을 마치거나 · 그만두거나 · 로그아웃하면 바로 지운다. 출생 정보는 두지 않는다.
- 비교: 같은 XSS 가 있으면 가입권을 두지 않아도 그 페이지에서 쿠키 세션으로(같은 출처 요청 · `credentials: 'include'`) 이미 같은 사람으로 서버를 부를 수 있다 — 가입권 보관이 XSS 가 없을 때의 위험을 새로 만들지는 않는다.
- 더 막으려면: CSP(스크립트 출처 제한)를 웹 응답에 둔다(`vercel.json` 헤더 — 지금 없다). 또는 웹만 가입권을 메모리에만 두고 이어 하기를 앱에서만.
- 결정 042 · 044 의 나머지(단계 · 값 · 별명 공개는 가입 직후 한 번 — 닉네임은 메모리)는 그대로다.
