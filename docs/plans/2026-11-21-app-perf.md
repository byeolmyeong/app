# 앱 성능 묶음 — 같은 조건 전/후로 재며 작은 PR 들로

> 상태: 제안(0 기준 측정 끝, 1~ 은 승인 뒤) · 요청: 소유자 "성능 최적화도 한 번 하고"(기능이 끝나 차례, 메모리 "기능 다 끝나면 성능 묶음") · 기준 develop `6a6148c` · 브랜치마다 새로(`perf/fonts` · `perf/splash-image` · `perf/bundle` …) · 웹 CSP 는 다른 담당(46)이라 건드리지 않는다

## 목표
- 무엇을: 처음 여는 사람이 스플래시에서 기다리는 시간과 받는 바이트를 줄인다. 웹이 먼저(가장 무겁다), 네이티브는 재 보고 판단한다.
- 누구를 위해: 처음 들어오는 사람(공유 · 랜딩에서 웹으로) — 스플래시가 길면 첫 화면을 보기 전에 떠난다.
- 끝나면: 아래 "검증" 표의 숫자가 줄어든 것을 같은 조건으로 보인다. 화면 · 동작은 그대로다.

## 측정 방법(같은 조건 전/후가 핵심)
- **웹(로컬, 비교의 기준)**: `npx expo export --platform web --source-maps`(`EXPO_PUBLIC_API_URL=http://localhost:4174`) → 로컬 정적 서버(Vercel 처럼 js · css · html · json · svg · otf 는 brotli, 그림 · woff2 는 그대로, `/x` → `x.html`) + 가짜 서버(세션 401 · 앱 설정만 — 처음 온 사람) → **Lighthouse 12.6.1 모바일 기본값**(느린 4G · CPU 4배 느리게 흉내, 이 맥의 Chrome headless, 깨끗한 프로필) **3회 중앙값**: 점수 · FCP · LCP · TBT · SI · 전송량, 첫 화면 전송 바이트를 글꼴 · JS · 그림 · 그 밖으로. 도구(서버 · 가짜 서버 · 3회 실행)는 작업마다 scratchpad 에 둔다(저장소에 넣지 않음).
  - 로컬 brotli 는 최고 압축(11)이라 Vercel(그때그때 압축)보다 작게 나온다 — 전/후 비교는 로컬끼리, 스테이징은 참고값.
- **웹(스테이징 참고값)**: `https://app.staging.byeolmyeong.com/` 에 같은 Lighthouse 3회.
- **번들 구성**: `source-map-explorer`(scratchpad)로 entry 의 패키지별 크기.
- **네이티브**: `npx expo export --platform ios` 의 Hermes 바이트코드(`.hbc`) 크기 · 함께 실리는 그림/글꼴 크기. 시작 때 기다리는 요청 수와 스플래시가 기다리는 것은 코드로 센다(아래). 차가운 시작 · 목록 · 그림 다시 그리기는 기기 빌드(테스트앱)에서 잰다 — 이 계획의 뒤쪽.

### 네이티브(iOS export)
- Hermes 바이트코드 **4.01MB**, 함께 실리는 파일 6.0MB(글꼴 **4.74MB** = 1.58MB × 3, 스플래시 346KB, 별이 288KB 등).

### 스플래시가 기다리는 것(코드)
1. **글꼴 셋**(`useFonts` — 웹은 3.2MB 내려받기, 앱은 4.7MB 읽어 등록)
2. 세션 확인 — 웹 `GET /auth/session`, 앱은 보안 저장소 → (토큰이 있으면) `GET /auth/session`
3. (로그인 전) 소개를 봤는지(AsyncStorage) · 가드가 보낼 곳으로 간 뒤
4. (로그인) 이용 정지 문 `GET /account`(많아야 3초)
5. (로그인한 홈) 홈의 첫 데이터 — 기기의 출생 정보, 없으면 되살리기 `GET /profile` → `POST /charts` + `GET /places`
6. 웹은 최소 0.8초 · 최대 10초, 앱은 최대 5초

### 시작 때 요청(코드로 셈)
- 로그인 · 기기에 데이터 있음: 스플래시가 기다리는 것은 **차례로 2번**(`GET /auth/session` → `GET /account`). 함께 `GET /app-config`. 홈이 뜨면 `GET /account`(**이용 정지 문과 같은 요청을 한 번 더**) · `GET /timing-report` · `POST /day-sky` · `GET /notifications`(+ 앱은 `POST /push/devices`).
- 처음 온 사람(웹 측정에서 본 것): `GET /app-config` · `GET /auth/session` · **`GET /places`**(가드 가림막 아래에서 홈의 출생 정보 입력이 먼저 그려져 곳 목록을 받는다 — 보내질 화면인데 받는 것) · 별이 그림 288KB(소개).

## 태스크(우선순위 순 — 각각 작은 PR, 테스트로 지킬 수 있는 것은 먼저, PR 마다 위와 같은 조건의 전/후 표)
1. **perf/fonts**(가장 큼 — 전송량의 67~71%, 스플래시가 기다림) · 상태: 완료(PR — 실행 기록)
   - 웹: woff2 + 부분 글꼴. 핵심 묶음 = 영문 · 숫자 · 기본 기호(U+0020–007E) + 앱 문구에 쓰인 기호(· › ‹ … “ ” 등, `strings.ts` 에서 뽑음) + **한글 KS X 1001 2,350자**. 나머지 한글(11,172자 중 2,350자 밖)은 두 번째 woff2 로 `unicode-range` 를 나눠, 그 글자가 화면에 있을 때만 브라우저가 받는다. 닉네임 · 문의 · AI 글에 드문 글자가 나와도 두 번째 묶음으로 같은 글꼴로 보인다(못 받으면 그 글자만 기본 글꼴 — PR 에 적는다). 굵기는 셋(400 · 500 · 600) 그대로(`FontWeight` grep — 셋 다 씀).
   - 앱: 글꼴은 기기에 실려 내려받기가 없다. 굵기는 셋 다 쓰므로 그대로 두고, 부분 글꼴로 앱 크기를 줄일지는 숫자를 보고(4.7MB → ?) 정한다.
   - 스플래시가 글꼴 셋을 다 기다리지 않게 할 수 있는지(예: 첫 화면에 쓰는 굵기만 기다림) — 글자가 바뀌어 보이는(FOUT) 일이 없을 때만.
   - 검증: 글꼴 전송 2.42MB → 목표 400KB 이하, LCP · FCP 감소, 화면 비교(소개 · 로그인 · 홈 · 나 탭)에서 글자 모양 같음, 드문 글자(예: "똠 · 쌰 · 뷁") 닉네임이 같은 글꼴로 보임.
2. **perf/splash-image** · 상태: 대기
   - `splash-icon.png` 346KB(300×300 표시, 실제 크기 확인) · `byeoli-default.png` 288KB → 크기 맞춤 + 최적 PNG 또는 webp(웹만 — 앱 스플래시는 PNG). 스플래시 preload 가 필요한지(LCP 요소라 preload 는 둘 가능성 큼, 크기를 줄이는 쪽).
   - 검증: 그림 전송 634KB → 목표 150KB 이하, 스플래시 · 소개 · 실패 화면 · 공유 카드 그림이 같아 보임(웹 이미지 저장 포함).
3. **perf/bundle** · 상태: 대기
   - `html2canvas-pro`(285KB) 를 "이미지 저장" 을 누를 때 받게(`import()` — 화면 조각 나누기(#57 반짝임)는 다시 켜지 않는다. 동적 import 의 조각이 웹 내보내기에서 따로 나오는지 먼저 확인).
   - 꺼 둔 음악(`expo-audio` 36KB)이 첫 번들에 들어오지 않게 할 수 있는지(결정 069 — 코드는 남김).
   - 검증: entry 원래 2.45MB · brotli 508KB → 줄어든 값, TBT, 웹 이미지 저장이 그대로 됨.
4. **perf/startup-requests**(작음) · 상태: 대기
   - 홈의 `GET /account` 를 이용 정지 문이 받은 것과 함께 쓰기(같은 요청 두 번) · 처음 온 사람에게 가드 가림막 아래 홈이 `GET /places` 를 받지 않게.
   - 검증: 시작 때 요청 수(가짜 서버 기록), 기존 시험 통과.
5. **화면 사이 기다림 · 네이티브** · 상태: 측정 뒤 판단
   - 웹: 탭 · push 사이 첫 그리기까지(이미 한 미리 받기는 빼고) — 프레임 기록으로 재고 큰 것만.
   - 앱: 테스트앱(기기)에서 차가운 시작 시간 · 큰 목록(태어난 곳 시·군·구) · 그림 다시 그리기. 숫자를 보고 따로 계획한다.
