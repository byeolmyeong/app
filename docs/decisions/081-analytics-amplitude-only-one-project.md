# 081. 1.0.0 제품 분석은 앰플리튜드만, 운영 프로젝트 하나로 보내고, 분석용 id 는 새 경로 `GET /auth/analytics-id` 로 받는다

> 상태: 활성 · 결정일 2026-11-26(소유자 — 애플 심사 전 마무리) · 결정 040 의 1(두 도구) · 6(환경 분리)과 "결과"의 `GET /auth/session` 줄을 대체한다. 040 의 2~5 · 7(이벤트 표 · 보내지 않는 것 · 사용자 구분 · 광고 id · 동의)은 그대로다 · 계획: docs/plans/2026-11-19-product-analytics.md

## 맥락
- 출시 순서(2026-11-26 소유자)에서 앰플리튜드를 애플 심사 전에 끝내기로 했다.
- GA4(계획 태스크 4·5)를 붙이면 네이티브 파이어베이스 모듈(`@react-native-firebase/*`)과 iOS 정적 프레임워크 설정이 새로 들어간다. 또 파이어베이스 앱 등록과 iOS 설정 파일도 더 필요하다. 심사 직전에 iOS 빌드를 바꾸는 위험이 크다.
- 040 은 앰플리튜드 · 파이어베이스 모두 스테이징 · 운영 프로젝트를 따로 두게 했다. 소유자는 "테스트는 왜 만들어??"라고 물었고, 하나만 쓰기로 했다.
- 040 의 서버 변경(`GET /auth/session` 204 → 200 `{ analyticsId }`)은 지금 앱의 웹을 깨뜨린다. 앱은 세션 확인을 빈 본문(204)으로만 받는다. 200 본문을 받으면 INVALID 가 되고, 웹은 '확인하지 못함'(offline, 결정 068 의 4)에 머문다.
  - 2026-11-26 jest 로 재현했다: `getSession → {"ok":false,"error":"INVALID","status":200}`, 웹 상태 `offline`.
  - 출시 순서가 서버 main → 앱 main 이라, 그 사이 운영 웹이 이 상태가 된다.

## 결정
1. **1.0.0 은 앰플리튜드만 쓴다.** GA4(파이어베이스 애널리틱스)는 1.1.0 광고(결정 015)를 붙일 때 다시 본다. 계획 태스크 4 · 5 는 1.1.0 으로 옮긴다. 이벤트 표 · 보내지 않는 것 · 값 목록 규칙은 040 그대로다.
2. **앰플리튜드 프로젝트는 운영 하나("별명")다.** 키 `EXPO_PUBLIC_AMPLITUDE_API_KEY` 는 EAS `production` 과 Vercel `byeolmyeong-app` 의 Production 에만 둔다.
   - 테스트앱(EAS `preview`) · 스테이징 웹 · 로컬에는 키가 없어 아무것도 보내지 않는다. 키가 없으면 콘솔에만 찍는 지금 코드 그대로다.
   - 키 값은 어떤 문서에도 적지 않는다.
3. **분석용 id 는 새 경로 `GET /auth/analytics-id`(200 `{ analyticsId }`, 세션이 없으면 401)로 받는다.**
   - `GET /auth/session` 은 204 그대로다. 더하기만 하므로 서버 · 앱을 어느 순서로 합쳐도 깨지지 않는다.
   - 값은 040 그대로: `"byeolmyeong-analytics:"` 을 앞에 붙인 계정 id 의 SHA-256 16진수 앞 32자, 저장하지 않음.
4. **앱은 키가 있을 때(운영)만 새 경로를 부른다.**
   - 한 세션에 한 번 받아 `identify` 하고 기억해 둔다. 부르는 때는 로그인 · 가입 성공 뒤, 그리고 앱을 켤 때 세션이 살아 있으면.
   - 로그아웃 · 계정 삭제 뒤에는 기억한 값을 지우고 `resetAnalytics` 한다.
   - 테스트앱 · 스테이징 · 로컬에서는 부르지 않아 서버 호출이 늘지 않는다.
5. **웹 CSP(결정 077) 의 `connect-src` 에 `https://api2.amplitude.com` 하나를 더한다.**
   - 앰플리튜드 SDK 는 앱 묶음 안에 들어가 외부 스크립트가 없다. 그래서 `script-src` 는 그대로다.
   - 기본 설정(US · 원격 설정 끔)에서 부르는 곳은 이 주소 하나뿐이다. 원격 설정 · 진단 주소(`sr-client-cfg` · `diagnostics`)는 `fetchRemoteConfig` 를 켤 때만 부른다. 켜면 정책도 더한다.
6. **출시 전 확인은 요청을 막고 본문만 본다.** 로컬 웹에 운영 키를 잠시 넣고, 앰플리튜드로 가는 요청을 브라우저에서 가로채 막는다. 운영 프로젝트에는 쌓이지 않는다. 그 본문에 출생 정보 · 공유 id · `code=` 가 없는지 본다. 실제 도착은 운영 배포(앱 main · 운영 iOS 빌드) 뒤에 확인한다.

## 근거
- 성공 지표(가입 · 차트 · 끝까지 읽음 · 공유 퍼널, 리텐션)는 앰플리튜드 하나로 다 잰다. GA4 의 몫(유입 경로 · 광고)은 1.1.0 에야 쓴다.
- 프로젝트를 하나만 두되 시험 환경에는 키를 넣지 않으면, 시험 이벤트가 운영 숫자에 섞이지 않는다. 그러면서 프로젝트와 키를 하나만 관리한다.
- 더하기만 하는 경로는 "어느 쪽을 먼저 올려야 하나"를 기억할 필요를 없앤다. 서버 · 앱 · 운영 · 스테이징 네 갈래 순서를 맞추지 않아도 된다.

## 대안
- 040 대로 GA4 도 지금 — 계획에 맞지만, 심사 직전 iOS 빌드 변경과 파이어베이스 준비가 늘어 심사 제출이 늦어진다.
- 앰플리튜드 프로젝트 둘(운영 + 시험) — 출시 전에 테스트앱에서 도착까지 볼 수 있다. 대신 프로젝트 · 키를 하나 더 관리한다. 소유자가 하나를 골랐다.
- `GET /auth/session` 을 200 으로 바꾸고 앱의 204·200 수용을 먼저 올리기 — 서버 변경은 작다. 하지만 앱 main 이 서버 main 보다 먼저 가야 해서 출시 순서와 부딪친다.

## 결과 · 재검토 조건
- 앱의 "204 · 200 둘 다 받기" 코드는 필요 없어 뺀다. `getSession` 은 그대로 204 만 받는다.
- 이벤트 표의 값 목록을 지금 화면에 맞춘다(계획의 "이벤트" 표가 단일 출처).
  - 해석 종류: summary(내 별명) · me_report(나 탭 풀이) · timing_report(시기 풀이) · day_sky(오늘의/그날의 하늘). 옛 report 는 없어졌다.
  - 공유 카드: nickname · me_area · day_sky · next_big(공유 v2 넷, 결정 053). 옛 링크의 READING · NEXT_TURN 은 그 뒤를 이은 카드로 센다.
  - 궁합 · 방향성 · 궁합 점수 · 랭킹 값은 1.1.0 을 위해 남긴다.
- 시험 환경에서는 앰플리튜드로 아무것도 가지 않는다. 이벤트가 오는지는 운영 배포 뒤 첫날 확인한다.
- 1.1.0 에서 GA4 를 붙일 때 040 의 1 · 6 을 다시 본다. 파이어베이스 프로젝트는 푸시와 같이 쓴다.
- 다시 볼 때: 시험 이벤트를 출시 전에 꼭 봐야 하면 시험 프로젝트를 하나 더 만든다(키는 EAS `preview` · Vercel 스테이징에).
